#### [Onboarding the Agentic Cloud Provisioning Platform to ACP: governing four traffic classes across a business-unit gateway](onboarding/agentic-cloud-provisioning/)
**Epic**: EACPP-1163 | **Gate**: D3 | **Type**: onboarding

The Cloud Infra AI Platform — the CAH Agentic Stack, also called the Agentic Cloud Provisioning
Platform — already runs durable cloud-infrastructure work behind its own Solo.io AgentGateway:
workload account provisioning, FinOps analysis, CMDB and APM lookups, software audit and incident
summary, executed as Temporal workflows with LangGraph agents in front and nine federated MCP
backends in between. It runs in test and expects to be production-ready within a week.

It is blocked for a governance reason rather than a technical one: an executive sponsor made
going through ACP a precondition for the ETAB submission. The deliverable that unblocks the team
is a defensible written statement of what ACP governs and what it does not, plus a working DEV
slice that demonstrates it.

ACP governs four traffic classes across one surface — front door, agent to Bedrock, agent to
tool/MCP, and agent to agent. No previous Sun Life use case has put all four through the gateway.
The integration is unusually cheap because ACP's gateway is the same agentgateway v1.4.1 binary
the team already runs, so MCP semantics are identical and there is no protocol translation.

Three findings shape the work. Gateway reachability is the only hard blocker: every ACP gateway
sets `slf.traefik.enabled: false` because no hostname, DNS record or certificate SAN exists
(EACPP-1155, Funnel). A gateway cannot run in the consumer's cluster — it is a luminate-portal
Helm release that dials an in-cluster service name and is admitted by a namespace-scoped
NetworkPolicy — so the buildable shape is CAH egressing to an ACP-hosted gateway. And policy's
finest target is an MCP server, not a tool, so read-only helpers and side-effecting provisioning
tools have to be split onto separate servers before "provisioning is governed" is true.

Calling Bedrock in CAH's own account is achievable but constrains topology: the gateway's
credential chain carries one `spokeRoleArn` per Helm release, so gateway count becomes
environments multiplied by spoke accounts.

On 2026-09-08 the OAuth question Temporal raises came in scope, having been parked at D0
approval. The answer is a shared root of trust rather than a new dependency: Entra issues for
Temporal (Web UI SSO, workers, namespace claims), ACP's Keycloak issues for callers into ACP,
and ACP identity travels one hop past the gateway to CAH's side-effecting backend via the
built token_forward mode. Temporal receives an assertion in the workflow input, never a token.
Making ACP the issuer for Temporal was rejected on the architecture - Luminate federates
identity inward and its own designs state the non-goal - not on preference. No platform
capability is required, so no gap is raised. This also corrected a factual error: the identity
mode enum has five values, not four, and the omitted token_forward is what the side-effecting
tier needed.

#### [Onboard the AI-Ready Data Use Case to ACP](onboarding/ai-ready-data-acp-integration/)
**Epic**: EACPP-1077 | **Gate**: D3 | **Type**: onboarding

ACP assists the Data Control Plane's AI-Ready Data use case with MCP server registration and testing on Luminate: register the AI-Ready Data MCP server in the Luminate catalog, publish its tools for discovery, route tool traffic through the governed gateway, provide a repeatable end-to-end test the use-case team can run unaided, and document the onboarding path in luminate-user-guides.

Supersedes the internal-build spec T1KACP/acp-specs/specs/ai-ready-data (EACPP-545), which proposed ACP as the runtime enforcement layer for the AI-Ready Data Framework — a DataProduct read model in acp-core, clearance intersection in the internal ai-gateway, clearance-to-Snowflake RBAC mapping, an AI-readiness lifecycle gate, Collibra lineage and compliance reporting. That scope is retired: the runtime is now Luminate, and ACP's role narrowed to registration, routing and testing. Classification, contracts, masking and RBAC remain with the Data Control Plane (DPEP / Sirius), which enforces them at the data tier.

Two planes, one guardrail chain: the Data Control Plane governs the data, ACP governs the agent's route to it. This spec builds only the seam.

h2. Problem Statement
• AI-Ready Data tooling is not registered in the Luminate catalog — use is not discoverable, scoped or audited
• No governed egress path — agents call the tooling directly, so no audit ledger entry, no policy check, no kill switch
• No repeatable test path for the use-case team to prove their MCP server works end to end against Luminate
• Onboarding requirements undocumented — what the team provides and what they get back restarts every conversation
• The seam between the two planes — an agent reaching certified data through a governed tool — is missing

h2. Opportunity
• The AI-Ready Data toolset becomes a first-class governed capability with no new runtime service
• A worked example of the two-plane model — DCP certifies the data, ACP governs the agent's route
• A reusable MCP onboarding path that aims, orcc and waldo also need
• Low cost and near-term — registration and testing against an already-deployed Luminate dev environment

h2. Acceptance Criteria
• AI-Ready Data MCP server registered in the Luminate catalog and visible to the use-case team
• Tools discoverable through the catalog with owner, scopes and tags populated
• Tool traffic routed through the Luminate gateway — authorized, traced, killable; no direct unaudited calls
• An invocation is retrievable end to end after the fact
• The end-to-end test is repeatable by the use-case team without ACP assistance
• Onboarding path published in luminate-user-guides and linked from the ACP onboarding guide

h2. In Scope (MVP)
• MCP server registration in the Luminate catalog (owner, project, scope tokens, mandatory tags)
• Tool catalog publication and discovery
• Governed routing through the Luminate gateway
• Repeatable end-to-end test: register, discover, invoke, audit, kill switch, latency comparison
• Onboarding documentation contributed to luminate-user-guides
• Harness SDK (acp-harness-sdk) integration where the use case calls programmatically
• Staged registration — read-only tools first, mutating tools second

h2. Out of Scope (Backlog)
• Runtime classification enforcement in ACP — clearance intersection, field-level allow/redact/deny, DataProduct read model
• Clearance to Snowflake RBAC mapping — Sirius Snowfort owns grants
• AI-readiness lifecycle gate — belongs in governance-intake as a per-band obligation if it returns
• Collibra lineage publishing and classification reconciliation
• Classification-compliance and masking-effectiveness reporting
• Authoring or running the AI-Ready Data Framework workflow — owned by the Data Control Plane
• Defining or changing the Sun Life classification taxonomy — consumed as-is

#### [Onboarding Corp IT's use case: AIMS (AI-Powered Incident Management System)](onboarding/aims-acp-integration/)
**Epic**: EACPP-909 | **Gate**: D3 | **Type**: onboarding

AIMS (AI-Powered Incident Management System) is an operations intelligence platform designed to reduce the time engineers spend diagnosing and resolving data platform failures. Currently detects AWS Glue job failures, collects diagnostics, uses generative AI for root cause analysis, and creates notifications. 

As a multi-agent system, AIMS evolves to include RCA Agent, Incident-Aware Agent, and Remediation Agent within a governed ACP control plane with MCP-based access to enterprise tools (Teams, Jira, knowledge repos, AWS operations). Goal is to transform reactive troubleshooting into intelligent, governed, and increasingly autonomous operations through ACP integration.

h2. Problem Statement
• AIMS currently lacks centralized governance, registration, and observability for its multi-agent architecture
• Agents (RCA, Incident Correlation, Remediation) operate without standardized policy enforcement or audit trails
• No unified platform for managing foundation models, requiring direct integrations instead of registry-based consumption
• MCP servers for enterprise tools (Jira, Knowledge Base, AWS Ops) lack centralized governance and control
• Operational costs and usage metrics for AIMS agents are not tracked or visible
• Each new agent capability requires custom governance implementation rather than inheriting ACP controls
• Risk: autonomous remediation agents lack sufficient oversight and approval workflows for production execution

h2. Success Criteria
• All AIMS agents (RCA, Incident Correlation, Remediation) successfully registered and managed through ACP agent registries
• Foundation models consumed through ACP model registries instead of direct integrations
• Cost and usage metrics for AIMS agents visible and tracked through ACP observability
• MCP servers for Jira, Knowledge Base, AWS Operations registered and governed through ACP MCP registries
• 100% audit trail coverage for all agent actions and model invocations
• AIMS leverages ACP for governance, policy enforcement, and execution monitoring
• New AIMS capabilities onboarded via ACP configuration and registration (no custom governance builds)
• Remediation agent recommendations and executions subject to ACP approval workflows

h2. Acceptance Criteria
• AIMS multi-agent architecture fully integrated with ACP agent registry API
• Agent registration, lifecycle, and deregistration workflows operational
• Foundation model registry integration tested with current models
• MCP server registry operational with Jira, Knowledge Base, AWS Ops connectors
• Agent observability dashboard showing execution metrics, latency, costs
• Audit trail captures all agent decisions and remediation actions
• Approval workflow enforced for remediation actions
• Cost attribution per agent per week/month visible
• Documentation for onboarding new AIMS agents to ACP

h2. In Scope (MVP)
• RCA Agent registration and observability through ACP
• Incident Correlation Agent registration through ACP
• Foundation model registry consumption (replacing direct integrations)
• MCP server registration for Jira, Knowledge Base, AWS Operations
• Cost tracking and attribution for agent usage
• Audit trail for all agent executions and decisions
• Basic approval workflow for remediation recommendations
• Observability dashboard showing agent health and metrics
• Documentation and runbooks for AIMS-ACP integration

h2. Out of Scope (Backlog)
• Remediation Agent autonomous execution (stage 2)
• Self-healing automation based on confidence scoring
• Advanced approval workflows with multiple stakeholder gates
• Cross-product incident correlation (only within AIMS scope initially)
• Predictive failure detection (phase 2 roadmap)
• Integration with external ticketing systems beyond Jira
• Multi-region AIMS deployment and coordination
• Real-time policy enforcement (reactive monitoring initially)

#### [Onboard Governance-by-Design Agents to ACP](onboarding/gbd-acp-integration/)
**Epic**: EACPP-1075 | **Gate**: D0 | **Type**: onboarding

Governance-by-Design (GbD) ACP Integration is the strategy to onboard GbD's own agents — and the AI4EA agent estate — onto the Agentic Control Plane running on Luminate: register the agents, register and route their MCP servers through the governed gateway, establish the gateway access pattern, track promotion across environments, capture audit logging, and obtain formal architectural approval of the integration pattern. Targets a GbD pilot in mid-October.

GbD runs the agents that assess everyone else's AI workloads, but those agents are not themselves registered, routed or audited by ACP. This D0 defines the scope, dependencies, stakeholders and success criteria for closing that gap.

Scope boundary: this spec covers how GbD's agents get onto the platform. How risk is assessed — questionnaire, obligations, bands, evidence — stays in governance-intake (EACPP-877) and governance-content-packs. The AI-assisted intake UI is specified separately in governance-intake-ui.

h2. Problem Statement
• GbD and AI4EA agents call models and tools directly — no registration, no gateway routing, no audit ledger entry for the agents performing governance
• No named agent inventory exists — specific agents, owners and onboarding requirements are not enumerated, so nothing can be converted into engineering tickets
• MCP server routing undefined — GbD agents reach ServiceNow, Archer and knowledge sources through unregistered tooling; tool calls are neither clearance-scoped nor audited
• Gateway access has no agreed path — harness SDK vs first-party workload identity vs delegated service identity is undecided and changes the work materially
• Architectural review not started — ACP communication patterns not documented in ServiceNow, ETG assignment outstanding, formal pattern approval required before production
• Two front doors, no decision — whether users stay in the GbD UI or move into ACP/Luminate is unsettled, so the onboarding surface is unknown
• Pilot has a date, dependencies do not — mid-October pilot targeted against an unsequenced dependency chain

h2. Opportunity
• Governance that is itself governed — the assessing agents run on the same control plane as the workloads they assess
• Reference onboarding for a governance workload — first use case whose agents read and write regulated systems of record (ServiceNow, Archer)
• A single approved integration pattern that later use cases inherit rather than re-litigate
• Closes the loop with governance-intake — GbD becomes both producer and consumer of the governance data product (FR-12)
• Mid-October pilot as a forcing function proving registration, routing, audit and UI handoff end to end

h2. Acceptance Criteria
• Named GbD and AI4EA agent inventory delivered and converted into engineering tickets
• In-scope agents registered in Luminate with owner, environment and lifecycle state visible in the catalog
• MCP servers registered and tool traffic routed through the governed gateway; no unaudited tool calls for onboarded agents
• One documented gateway authentication path implemented and working in dev
• Agent promotion between environments demonstrated with the transition recorded
• Audit ledger populated — invocations and tool calls retrievable per agent
• Integration pattern formally approved — ServiceNow documentation complete, ETG assigned, approval obtained
• Front-door decision recorded and the API handoff specified
• Mid-October pilot live with the named agent subset under ACP governance

h2. In Scope (MVP)
• GbD + AI4EA agent inventory with owners, contacts and per-agent onboarding requirements
• Agent registration in Luminate across promotion environments
• MCP server registration and governed gateway routing

#### [Onboarding Vulcan to ACP: governed inference and tool access for remediation-as-a-service](onboarding/vulcan-onboarding/)

Two gaps decide the shape: machine-to-machine authentication is default-off in every Sun Life environment and its trusted issuer is a single value that does not match Vulcan's Okta tokens (blocks the dispatch gate); and MCP `INJECTED_CREDENTIAL` is not implemented, so a PAT-fronted Bitbucket or scanner backend cannot be credentialed by the gateway (blocks brokered tool access). The inference half depends on neither, which is why it ships first.

#### [Luminate Gateway & Environment Strategy](platform/gateway-environment-strategy/)
**Epic**: EACPP-1089 | **Gate**: D3 | **Type**: platform

Target topology for how Sun Life runs the DEV / SIT / STAGE / PROD workload environments of the production Luminate control plane: one production control plane governs every environment and region, and each environment's gateways run in that environment's own AWS workload account (dev, test for SIT, stage, prod), in each serving region (today ca-central-1 and us-east-1, with a defined procedure for adding further regions), calling Amazon Bedrock in that same account.

Revised 2026-10-06 after the Luminate Gateway Environment Deployment Model session, which agreed this middle ground in response to section 2.3 of the Infrastructure, Platform and Network Security Directive. The only communication between environments is each gateway's outbound, authenticated, content-free control link to the control plane, submitted for approval through a new ATG and ISRA.

h2. Problem Statement
• All eight gateways run in the production account, so non-production and stage traffic, Bedrock use and operator access sit there
• No ATG or ISRA covers one control plane governing gateways in other environments' accounts
• Segregation of duties between platform administration and business use is not documented end to end
• The portal cannot yet separate deployment authority by environment, and separated governance duties are switched off
• Gateway trust assumes the production account: identity is taken from the request and signing keys are fetched in-cluster
• Gateway hostnames name clusters, so every move breaks agent configuration
• The test and stage accounts have no us-east-1 cluster

h2. Opportunity
• Each environment's traffic, Bedrock spend and blast radius in its own account, with one governance record across all of them
• Cross-environment communication reduced to one enumerable, inspectable control link per gateway
• Promotion that is self-service in DEV and SIT and approval-gated in STAGE and PROD, with no production change on one person's authority
• Gateway moves invisible to business teams through friendly hostnames

h2. Acceptance Criteria
• ATG and ISRA decided for the topology and its control link
• Every account has a cluster in each serving region; each environment's gateways run in its account and call Bedrock there
• A further region can be added by a published procedure, with no design change
• Gateways are trusted only as themselves and reach the control plane only over the control link
• Every gateway is on a friendly hostname that business teams use
• Deployment authority is per environment; STAGE and PROD promotion runs through approval chains that exclude the requester and owner; governance duties are separated in code; every production change is maker-checker
• Model Risk's checklist enforces in STAGE and PROD and observes in DEV and SIT
• One workload promoted DEV to PROD across the four accounts; no business workload on a lower install

h2. In Scope
• Gateway placement per account and region; the high-level architecture and data flows
• The control link and its position against IPNSD 2.3; gateway trust
• Segregation of duties, personas and the promotion process
• Governance per environment; data isolation; availability of the control plane
• Friendly gateway hostnames; the missing us-east-1 clusters
• The procedure and naming for adding further serving regions
• The ATG and ISRA package

h2. Out of Scope
• Deploying or upgrading the control plane itself - sunlife-deployment (EACPP-596)
• Relocating the control plane to us-east-1 - us-cutover (EACPP-1407)
• Gateways operated by business units - consortium Federated Gateways (ACPDIS-124)
• Authoring Model Risk's rule content - acp-cmrm-policy-as-code, governance-content-packs
• Onboarding any specific use case

#### [Guardrails Enablement: turning on content inspection at the Luminate gateway](platform/guardrails-enablement/)
**Epic**: EACPP-1295 | **Gate**: D3 | **Type**: platform

Luminate ships a complete guardrails subsystem — catalogue, eight attachment scopes,
strictest-wins resolution in the policy engine, and block / redact / warn enforcement at the
gateway on both the request and the response side. The images Sun Life already runs contain all
of it. None of it is switched on.

Measured 2026-09-11: the DEV install holds zero Guardrail rows, zero attachments and zero
evaluations; all four PROD-install gateways carry a six-key gateway ConfigMap with no
GATEWAY_GUARDRAIL_* entry; and luminate-sunlife-deploy contains no guardrail, PII-detector or
Model Armor configuration in any values file or template. CAP-10 is graded Available and
Mandatory, which is true of Luminate and not true of our deployment.

Three properties of the implementation decide the rollout. Only banned_words runs in-process;
pii_detection and model_armor are HTTP sidecars that must be named in
GATEWAY_GUARDRAIL_REMOTE_ENDPOINTS, and that map defaults to empty. A guardrail whose evaluator
cannot be resolved fails OPEN by default, so attaching a PII control before its sidecar exists
produces a portal that reads "attached" over traffic that is not scanned. And streamed
responses are exempt by default, which the upstream D2 records as an unmet requirement (NFR-7).

Phase 1 is Sun Life enablement: deploy the evaluators, wire the configuration, set the fail
posture deliberately, author a first control set, and prove enforcement end to end in DEV before
PROD. Phase 2 is an AWS Bedrock Guardrails evaluator, which has no upstream existence in any
form and needs a consortium ballot idea before it can be ranked.

#### [ACP / Luminate Integration Patterns](platform/integration-patterns/)
**Epic**: EACPP-1112 | **Gate**: D3 | **Type**: platform

The catalogue of supported patterns for integrating an existing application with ACP / Luminate: how it authenticates, how it reaches models, MCP tools and other agents, and where model inference actually executes.

Seven use cases are specced for onboarding and each is rediscovering the same integration decisions. This spec gives them a decision tree and one page per pattern, so an onboarding spec references a pattern rather than inventing one.

Covers the four credential shapes the gateway accepts, the portal client-credentials exchange and its rate limit, the three invocation surfaces (/llm, /mcp, /a2a), and the two model inference patterns. Inference is separated into two axes: where the Bedrock call executes and therefore who AWS bills (consumer-account, where the gateway assumes a role provisioned into the consumer's account by the published acp-aws-service-catalog product; or centralized, where Bedrock is enabled in the ACP workload account and ACP fronts the spend), and where the workload runs (team AWS account, Bedrock AgentCore runtime, or OpenShift/Kubernetes). In both billing patterns the gateway makes the call; the workload never holds a Bedrock credential.

Every pattern carries a maturity label - works today, partial, or blocked - because a catalogue that does not distinguish working from aspirational is worse than no catalogue. Mechanics live in luminate-user-guides; this spec owns which patterns exist.

h2. Problem Statement
• No pattern catalogue exists - a team asking how to call a governed model gets a conversation, not a page, and the answer varies by who they ask
• The credential story is non-obvious - a credential belongs to a (resource, gateway) pair, is shown once, and does not exist until the resource is deployed
• Registration and invocation have different answers today: the gateway data path works with a machine credential, the catalogue path does not, because registry machine-to-machine auth is default-off
• The gateway accepts four credential shapes with different validation and different eligibility per endpoint; an MCP delegated endpoint refuses an API key with a 403 that looks like a policy denial
• Two model inference billing patterns are conflated with where the workload runs, and which applies decides who AWS bills and whether chargeback is needed at all
• Teams without an AWS workload account - Strands agents on OpenShift being the motivating case - have no documented path; only centralized serves them, which is why chargeback gates it
• The ACP hub account is SCP-denied from bedrock:*, which is why role-chaining into a consumer spoke exists at all, and why centralized needs an organisation-level SCP change rather than configuration

h2. Opportunity
• One page per pattern, chosen by a decision tree
• The onboarding specs stop re-deriving and their D1s get shorter
• The non-AWS path becomes real - centralized inference gives OpenShift and Kubernetes workloads a supported route to Bedrock
• Chargeback gets a stated position rather than an assumption
• The harness SDK makes call sites portable between builds and between environments as configuration, not code

h2. Acceptance Criteria
• A team can pick its pattern from a diagram without asking the platform team
• Each pattern states its credential shape, invocation path, failure modes and maturity label
• The two inference billing patterns are distinguished, with who AWS bills and whether chargeback is needed
• A workload with no AWS account has a documented, supported route to a governed model
• The chargeback position is explicit - what exists, what does not, what would be needed
• The onboarding specs reference this catalogue instead of re-deriving
• Every gap is a named consortium ask, not a local workaround

h2. In Scope
• Pattern catalogue with a decision tree
• Identity and credentials - the four shapes, Keycloak and portal flows, token exchange, TTL, caching, storage
• Gateway invocation - /llm, /mcp, /a2a paths, authorization, failure modes
• MCP patterns including the delegated on-behalf-of path
• Model inference patterns - consumer-account (gateway assumes into the consumer's account, AWS bills the consumer) and centralized (Bedrock in the ACP workload account, chargeback required), plus the hosting shapes that compose with them
• Cost attribution and chargeback - what exists and what does not
• Adoption paths - harness SDK versus raw HTTP, and what registration actually requires today
• Gaps and the consortium asks that unblock them

h2. Out of Scope
• Environment and gateway topology - gateway-environment-strategy (EACPP-1089)
• Onboarding any specific use case - each has its own spec
• Governance intake and risk classification - governance-intake (EACPP-877)
• Building the SDK - acp-harness-sdk (EACPP-791) and aws-harness-integration (EACPP-707)
• Gateway internals - routing, guardrails and the proxy data path are consortium-owned
• Deploying Luminate - sunlife-deployment (EACPP-596)
• Authoring the end-user guides - luminate-user-guides is the canonical home

#### [Agent Patterns — Building, Hosting, Registering and Invoking an Agent](pattern/agent-patterns/)
**Epic**: EACPP-1290 | **Gate**: D3 | **Type**: pattern

The generalized pattern for how an agent is built, hosted, registered, governed and invoked on ACP / Luminate, and the conformance requirements an agent must meet before the platform will serve it.

An MCP server is only ever a callee. An agent is both, and the two directions are separate registrations with separate requirements. **Egress** — the agent as caller, reaching models over `/llm`, tools over `/mcp` and other agents over `/a2a` — is what most teams mean by "onboard my agent". **Ingress** — the agent as callee, invoked by another agent over `/a2a` — is a different endpoint, a different credential and a different authorization question. A team that registers for egress and assumes its agent is now callable is the failure mode this pattern exists to prevent.

Covers the catalogue and lifecycle model, the egress governance surface (source policies, credential shapes, where credentials actually hang), the ingress A2A lane as it now runs (route translation, the on-behalf-of exchange, RFC 9728 discovery, withholding), four hosting substrates with a requirements annex each, the approved Jenkins JTE build path, and the operational surface — audit, tracing, run correlation and the stop path.

Every requirement carries an enforcement point and a verification method, and every absence is a search that returned nothing.

h2. Problem Statement
• Egress and ingress are conflated. Registering an agent and granting it a model makes it a governed caller; it does not make it callable. Nothing in the product or the guidance says so, and eight of the ten agents registered in dev are egress-only without anyone having decided that
• The stop control is asymmetric and nobody has stated it. Setting an agent inactive denies every A2A call *to* it, and denies nothing it does: the rego matches a source policy on the JWT subject alone and never consults the agent's status. Deactivating a misbehaving agent does not stop it reaching a model
• Governance state is modelled, audited and inert — zero references in the policy engine, the access-policy app, the gateway and every Rego package. The suspension module says so itself: "the state is real and the denial is not"
• Guardrails cannot be attached to an agent as a callee. There is no target-agent scope and no agent branch in the Rego, so content control on the A2A lane exists only if every caller happens to carry one
• The two environments disagree about what an A2A call even is. Dev serves both A2A routes with an on-behalf-of token exchange; prod runs a build that predates it and serves the same shape with no credential at all
• The A2A discovery contract cannot be met through the gateway — nothing in the platform serves or proxies an agent card, and `/.well-known/` is answered locally
• The adoption path does not reach the lane it advertises. The harness SDK's A2A method sends no credential, and its default gateway credential is the one shape a delegated A2A endpoint refuses
• Substrate is unbounded — OpenShift, EKS, Bedrock AgentCore and Lambda each have a different reachability, TLS, identity and cold-start story, written down nowhere
• There is no ETAB or ISRA artefact for the agent lane

h2. Opportunity
• One conformance profile — ASR-1 to ASR-38 — assessed once per agent and reusable for every ISRA
• Egress and ingress become two named decisions with two requirement sets, so "is my agent callable" stops being a support question
• The stop control becomes honest: what it reaches, what it does not, and what an operator must do instead
• A decision tree by substrate, so a team picks its shape without a meeting
• ETAB gets one architecture, one control table and a named residual-risk set
• The onboarding specs stop re-deriving the agent half of their design

h2. Acceptance Criteria
• A team can determine, from one page, what its agent must satisfy in each direction it operates
• Each hosting substrate states its reachability, TLS, identity, egress and build requirements
• The stop path is stated with what it does and does not reach, and its propagation is measured rather than quoted
• Every conformance requirement has an enforcement point, a verification method and an owner
• Any hosting platform outside the four specified substrates has a published set of criteria it is assessed against, and an open criterion rather than a refusal where it falls short
• assurance.md is sufficient on its own for the ETAB submission and the ISRA control table

h2. In Scope
• The agent conformance profile — direction, catalogue, identity, authorization, supply chain, runtime, data, observability and lifecycle
• Registration and deployment: what the catalogue requires, what makes an agent reachable, and where credentials hang
• Egress governance — source access policies, credential shapes, the guardrail and quota position
• Ingress / A2A — route translation, the delegated exchange, withholding, RFC 9728 discovery, and the agent-card gap
• Hosting substrates S1 OpenShift, S2 EKS, S3 Bedrock AgentCore, S4 AWS Lambda, plus the SUB-E / SUB-I admission criteria any other platform is assessed against
• The approved Jenkins JTE build path and its scanning gates
• Operations — audit, tracing, run correlation, cost attribution and the stop path
• The ETAB architecture and the ISRA control table

h2. Out of Scope
• Building any specific agent — this spec states requirements, not implementations
• The MCP server an agent calls — mcp-server-patterns (EACPP-1176)
• The credential, invocation and inference patterns shared with every lane — integration-patterns (EACPP-1112)
• Gateway and environment topology — gateway-environment-strategy (EACPP-1089)
• Re-specifying the harness SDK — acp-harness-sdk (EACPP-791) is referenced, not redesigned
• Agent framework selection — LangGraph, Strands, Bedrock AgentCore and the rest are substrate, not governance
• Gateway internals — routing, guardrail evaluation and the proxy data path are consortium-owned
• Authoring the end-user guides — luminate-user-guides is the canonical home

#### [Model Inference Patterns — Centralized Inference, Cost Attribution and Model Access Governance](pattern/model-inference-patterns/)
**Epic**: EACPP-1320 | **Gate**: D3 | **Type**: pattern

The target-state pattern for where a model call executes, who may make it, and who pays for it on ACP / Luminate.

Inference executes in the ACP production workload account, through the gateway serving the calling workload's environment and region — one gateway per environment per region, per gateway-environment-strategy DD-3. The workload names a model and holds no provider credential; which provider serves it, in which account and which region, are platform decisions resolved through the catalogue.

Centralized inference is the target state for three reasons. It is the only shape that serves a workload with no cloud account. It presents a single measured enterprise demand to a provider, which is the precondition for committed-spend agreements and negotiated inference deals. And it keeps the provider replaceable, because moving a model between providers is a catalogue change rather than a migration per consuming team. Bedrock is the provider today; the pattern does not assume it is the provider tomorrow.

Aggregating the bill is only safe if it stays decomposable. In a distributed shape the cloud account boundary attributes spend for free; centralizing removes that boundary, so ACP becomes the attribution authority — a daily ledger at (project, entity, user, model, provider) grain carrying a cost centre, reconciled against the provider invoice before anything is charged, delivered into the enterprise chargeback pipeline finance already runs. A single bill the platform cannot decompose is not leverage, it is a liability.

Covers the topology and the decision behind it, the attribution chain end to end, budgets enforced at the call, model access governance — which agent, user, application or project may call which model in which region — and the ETAB architecture with an ISRA control table.

Every requirement carries a verification method. D2 states the target state; the delta between it and the platform as it stands is D3, so approving the pattern and scheduling the work are separate decisions.

h2. Problem Statement
• The centralized-versus-distributed decision is unmade and load-bearing — integration-patterns T16 (EACPP-1128) says in terms "decide and record whether centralized is offered, and to whom", and seven onboarding use cases are waiting on the answer
• Without a centralized call path the enterprise has no aggregate inference volume, only many small ones, so committed-spend agreements and negotiated rates are not available to it
• A workload that calls a provider endpoint directly has hard-wired that provider into itself, so changing provider later costs a migration per team rather than a catalogue change
• Centralizing inference removes the cloud account boundary that attributes spend today, so without a deliberate attribution design the model costs of every business unit land undifferentiated on the platform's budget
• A workload with no cloud account — an agent on OpenShift, a desktop client product, an Office add-in — has no governed route to a model at all
• There is no stated position on how spend is limited, who may call which model in which region, or what a business owner is promised about either
• There is no ETAB or ISRA artefact for the inference lane — no single architecture to present and no control set to assess

h2. Opportunity
• One recorded decision on centralized inference, discharging T16 and unblocking the onboarding specs waiting on it
• Inference becomes a negotiable commercial position rather than a distributed cost
• The provider becomes replaceable without touching a consuming workload
• An attribution chain that keeps an aggregated bill decomposable to project, user, model and cost centre
• A chargeback design that feeds the existing enterprise pipeline rather than competing with it, so finance keeps one view of cost-centre spend
• Spend bounded by budgets enforced at the call, bound to the accountable owner, with what is promised equal to what is enforced
• Model access governance expressed once: agent, user, user group, application and project as sources; model, region and environment as the scoping dimensions
• ETAB gets one architecture and one control table, and the onboarding specs stop re-deriving the inference half of their design

h2. In Scope
• The inference topology — where a call executes, which gateway serves it, and the decision behind it
• The attribution chain — token capture, pricing, ledger, cost centre, reconciliation, and the hand-off to the enterprise chargeback pipeline
• Measurement integrity as a control, including complete token-dimension capture and pricing-catalogue currency
• Budgets — what is limited, how it is enforced, who owns a limit, and what a business owner is promised
• Model access governance — sources, targets, region and project scoping, and lifecycle
• The ETAB architecture and the ISRA control table for the inference lane

h2. Out of Scope
• Onboarding any specific workload — this spec states the pattern; anthropic-client-acp-integration and the other use cases consume it
• The credential, invocation and hosting patterns shared with every lane — integration-patterns (EACPP-1112)
• Gateway and environment topology, and which gateway serves which environment — gateway-environment-strategy (EACPP-1089)
• Agent registration, ingress and the agent conformance profile — agent-patterns (EACPP-1290)
• MCP server registration and the tool lane — mcp-server-patterns (EACPP-1176)
• Building the enforcement mechanism — a consortium dependency raised here (AIC-20, AIC-43, EACPP-834), not solved here
• Intelligent routing, semantic caching and cost-aware model selection — EACPP-20, deliberately excluded so the governance question is settled first

#### [Governance and compliance requirements for Luminate from US](governance/luminate-control-plane/)
**Epic**: EACPP-913 | **Gate**: D0 | **Type**: governance

Luminate Control Plane is the enterprise-wide AI governance and compliance platform consolidating 27+ regulatory frameworks (NAIC, OSFI E-23, Colorado CAIA, EU AI Act, HIPAA, NIST, OWASP, Texas TRAIGA, NYDFS, PIPEDA) and 14+ Sun Life internal policies (MBCT, IT Risk, Technology Architecture, AppSec, Privacy, Logical Access, Data Classification, Business Continuity, Records Management) into a unified control plane for scaled AI agent deployment.

The platform implements five core compliance primitives: (1) unified compliance requirement registry mapping all regulatory/policy obligations to product controls with unique CR-IDs; (2) automated compliance passport workflows routing agent registrations through required governance tracks (ATG, ISRA, MBCT, PIA, TPRM, Records) with blocking gates; (3) risk-tier-driven enforcement (AA/A/B/C/D risk levels) automatically gating killswitches, PIAs, validation workflows, and audit fidelity; (4) immutable compliance audit ledger recording all governance decisions and agent actions; and (5) graduated governance primitives (killswitches, HITL, key recertification, purpose-based access control) preventing uncontrolled agent proliferation.

This D0 consolidates compliance strategy for the first production release to US DCP, with blockers and required-before-scale work identified and prioritized.

h2. Problem Statement
• Sun Life's AI governance is fragmented across 27+ regulatory frameworks and 14+ internal policies with no unified platform consolidating requirements into actionable controls
• Manual compliance passport process requires hand-offs across six governance tracks (ATG, ISRA, MBCT, PIA, TPRM, Records) with no automated workflow confirmation before activation
• Without automated risk classification (AA/A/B/C/D), the platform cannot enforce that high-risk agents have killswitches, HITL, full-fidelity audit, and PIAs while low-risk agents have lighter controls
• Compliance reporting requires manual assembly of logs and evidence from disparate systems; no unified audit ledger for regulatory discovery
• No platform-enforced mechanisms for multi-gateway killswitches, HITL holds, key recertification, or purpose-based access control
• AI agents provisioned as human-like accounts rather than governed non-human identities (NHIs) with controlled lifecycles
• Compliance decisions not recorded in immutable audit trail discoverable by regulators for incident investigation and compliance reviews

h2. Opportunity
• Unified compliance registry consolidating all 27+ regulatory and 14+ policy requirements into platform-enforced controls
• Automated compliance passport workflows with T0 triage gating and evidence collection across all tracks
• Risk-tier-driven enforcement automatically scaling controls (killswitch, PIA, audit fidelity) based on agent risk classification
• Immutable compliance audit ledger supporting regulatory discovery and audit evidence export
• Graduated governance primitives (killswitch, HITL, recertification, PBAC) enabling scaled deployment of L1-L4 agents
• Non-human identity lifecycle management integrated with enterprise IAM (Okta, Azure AD)
• Regulatory evidence dashboard and exportable compliance packs for OSFI, NAIC, state insurance commissioners
• Multi-jurisdiction policy enforcement for Colorado, Texas, Canada, EU regulatory requirements

h2. Acceptance Criteria
• All 40+ compliance requirement sources (CR-EXT, CR-MBCT, CR-ITR, CR-ARC, CR-APP, CR-IPNSD, CR-ASM, CR-CHG, CR-POG, CR-LAS, CR-ICP, CR-BCM, CR-IMR, CR-GEN, CR-PBAC, CR-CC) mapped to unique CR-IDs and platform primitives
• Compliance passport workflow fully automated: agent registration triggers T0 triage; ATG, ISRA, MBCT, PIA, TPRM, Records evidence collected via platform; activation blocked until all tracks complete
• Risk tier field (AA/A/B/C/D) on Agent model with automatic gating of killswitch attachment, PIA requirements, validation_status, audit fidelity, key rotation cadence
• Killswitch primitive: atomic multi-gateway halt (per-agent/per-project/per-org); tested and exercised in security drill; SLA <5 seconds to global suspension
• HITL primitive: hold/review/decision/release workflow for agent responses; Level A/AA agents cannot be deployed without HITL capability
• Key recertification workflow: tier-driven rotation schedule (L1=365d, L2=180d, L3/L4=90d); automated reminders; auto-revoke on expiry; zero keys active past expiration
• Output guardrails: PII detection/redaction and bias/discrimination classification on model responses; 95%+ precision on PII redaction
• Full-fidelity audit for Level A/AA: AuditEvent records with plane, event_class, sensitivity, fidelity, outcome, protocol type
• PBAC enforcement: purpose declaration on invocations; purpose-driven data access gates; purpose drift detection alerts
• Non-human identity integration: agent API keys registered as service accounts in Okta/Azure AD; NHI inventory queryable by IAM team; zero human accounts used for agents
• Regulatory evidence dashboard: exportable compliance packs for OSFI E-23, NAIC, Colorado CAIA, HIPAA within 1 business day
• Multi-jurisdiction constraints: Colorado consumer notification, Texas discrimination prohibitions, Canadian data residency, HIPAA safeguards auto-enforced per deployment location

h2. In Scope (MVP)
• Compliance requirement registry (CR-ID mapping for 40+ sources)
• Risk tier field and tier-driven governance enforcement
• Killswitch primitive (atomic suspension)
• HITL primitive (hold/review/release)
