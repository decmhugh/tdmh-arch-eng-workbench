## Capability map

Three documents, one job: the single list of what ACP can do for a use case. **Luminate-only**
— the Sun Life internal MVP is not a delivery target and does not appear as an alternative.

| File | Answers | Verified against |
|---|---|---|
| `docs/capability-map-summary.md` | *What is the shape of coverage?* | Generated — never hand-edited |
| `docs/capability-map.md` | *What can ACP do **today**?* | Built code on `AI-Consortium/luminate` `origin/main` |
| `docs/capability-roadmap.md` | *What is **coming**, when, and what can I vote for?* | `luminate-designs`, `AIC` epics, `ACPDIS` ideas |

The catalogue is the menu walked through in use-case discovery, and every `onboarding` and
`integration` spec is written against it:

- **D0** carries a Capability Requirements table — mandatory baseline acknowledged, plus the
  capabilities the use case selects, with a business reason and a priority.
- **D1** traces every functional requirement to a capability ID, and opens a Capability Gaps
  row for anything not fully available.

Two rules govern its use, both from the D0/D1 definition session:

1. **Capabilities are confirmed, never inferred.** A transcript summariser reading "kill
switch was not mentioned" as "kill switch not required" is the failure this prevents.
2. **The mandatory baseline applies whether or not it is requested.** Governance obligations
do not move because a use case did not raise them.

Gaps route through `docs/process/capability-gap-escalation.md`. The delineation: a change to
Luminate itself goes to the consortium as an idea; making ACP reach a Sun Life system is
integration and the harness absorbs it. An ask that never becomes an `ACPDIS` idea **cannot be
ranked** at a Product Board round, which is why `capability-roadmap.md` §6 exists.

To refresh any of the three: `/capability-map-refresh`, or read
`.github/skills/capability-map-refresh/SKILL.md` — it carries the source-to-column mapping and
the built-vs-enforced protocol. Directory-scoped rules are in `docs/AGENTS.md`. Re-verify
against `AI-Consortium/luminate` **`origin/main`** — never a fork, mirror or feature branch —
and update the `Last verified` SHAs. See
`.github/instructions/capability-mapping.instructions.md` for how specs consume the map.

### Diagrams and the summary sub-page

The map publishes as two pages, summary first. Both diagrams and the summary page are
**generated from the §4 catalogue tables** — nothing here is hand-drawn, so the picture cannot
drift from the table underneath it.

```
ACP Capability Map — At a Glance   (113216356466)   one screen, every card a link
└─ ACP Capability Map (Luminate)   (113134797174)   the full catalogue and evidence
```

| Artifact | Source | Published as |
|---|---|---|
| `docs/assets/capability-map-summary.svg` | §4 tables + §6/§6a counts | draw.io macro on `113216356466` |
| `docs/assets/capability-map.svg` | §4 tables | draw.io macro on `113134797174` |
| `docs/capability-map-summary.md` | hand-written, links back to the catalogue | the parent page |

Each capability card deep-links to its row on the detailed page (`…/113134797174#cap-01`).

To recreate both from scratch:

```bash
python3 scripts/render_capability_map.py --export     # .drawio + .svg for both views
CONFLUENCE_SPACE_KEY=T1KACP python3 scripts/sync_to_confluence.py --capability-map
```

Six things that will bite:

1. **`CONFLUENCE_SPACE_KEY` must be `T1KACP`.** The shared credential file exports `DPEP`,
   which overrides the script default and publishes into the wrong space. Set it inline on
   the command — do not rely on the default.
2. **`--dry-run` writes fake `dry-…` ids** into `references/confluence-page-mapping.json`.
   Purge them before a real run or the script believes the pages already exist.
3. **Every page's parent is explicit, and unmapped is a hard failure.** A spec's parent comes
   from its `spec_type` (`SPEC_TYPE_PARENTS`), a living document's from its title
   (`STANDALONE_PAGE_PARENTS`). An unrecognised `spec_type` raises rather than defaulting —
   the old default published into what is now an archived tree, which the API accepts
   silently.
4. **`references/confluence-page-mapping.json` is state.** Its keys encode the parent
   (`{parent_id}/{title}`), so changing the hierarchy means re-keying it — run
   `scripts/reconcile_page_mapping.py --write`, which reads each page's real parent so ids and
   history survive. A run that creates a page writes its id there — commit the change or the
   next run creates a duplicate.
5. **The sync never re-parents an existing page**, by design: `ancestors` is sent only on
   create. This space is curated by hand — the living documents currently sit under
   *3. Product & Engineering → Design Process & Decisions*, not under the repo's own root
   page — and forcing ancestors on update would rip them out of that structure on every run.
   Move a page deliberately with
   `PUT /rest/api/content/{id}/move/append/{targetId}`, and note it refuses a move that would
   make a page a descendant of itself, so a parent/child swap takes two calls.
6. **`diagramName` on the draw.io macro must include the `.drawio` extension.** With the bare
   stem the macro is accepted and stored and then renders *nothing* — no error, no
   placeholder, just a gap. Verify a publish by counting `drawio` in `body.view`; zero means
   it silently failed.
7. **A deep link on a diagram shape needs `lbox=0` and `links=blank`.** The macro runs in a
   Connect iframe and routes clicks itself; its lightbox viewer takes the click before the
   browser sees a navigation, so the URL fragment is dropped and the reader lands at the top
   of the target page. `links=blank` forces a full document load — the reader gets a new tab,
   which is the mechanism rather than a side effect. Confluence's own anchors are fine; if a
   deep link misbehaves, test a plain link against a diagram link before touching the URL.

The draw.io export flags in `render_capability_map.py` are load-bearing — see the module
docstring before changing them. Short version: `--embed-svg-fonts false` stops labels being
rasterised into a base64 blob, and `html=0` on every shape stops them being buried in a
`foreignObject`. Both failures render a diagram with no readable text, and neither is visible
locally in a browser.

`INTERACTIVE_DIAGRAMS` in `sync_to_confluence.py` opts a diagram into the draw.io macro instead
of a flat `<ac:image>`. It is the only embed that keeps per-shape links clickable; an SVG served
through an `<img>` tag swallows them. Every other `.drawio`/`.svg` pair in the repo keeps the
plain image embed.

## Development Standards

**Spec Format**: Markdown with YAML frontmatter metadata. Mermaid diagrams for architecture.

**Git Workflow**:
- Branch per spec gate: `spec/{component}/d{N}` (e.g., `spec/agent-registry/d1`)
- PR to `main` for each gate advancement
- Reviewers assigned based on gate type (see D0→D4 table)
- Squash merge with conventional commit: `spec(agent-registry): advance to D1`

**Review Process**: Each gate requires explicit PR approval before advancing.

## spec.yaml required fields

Every `specs/<spec_type>/<component>/spec.yaml` must carry these, or `validate_specs.py` fails:

| Field | Values | Notes |
|---|---|---|
| `component` | dir name | must match the directory |
| `title` | string | human-readable component name |
| `current_gate` | `D0`–`D4`, `done` | the gate. **Not** `status` |
| `status` | `draft`, `in-review`, `approved`, `not-started` | document lifecycle |
| `jira_epic` | e.g. `EACPP-909` | the join key for the index and the O7 report |
| `spec_type` | `onboarding`, `integration`, `platform`, `governance`, `pattern` | classification |

`spec_type` decides how a spec is grouped in the index and which workstream it
rolls into on the O7 Weekly Delivery Synthesis:

- **onboarding** — bringing a business-group use case onto ACP (AIMS, ORCC, MDx, Waldo, US team)
- **integration** — connecting an existing system to ACP (NOVA, AWS Harness)
- **platform** — an ACP product capability itself (SLM pipeline, Harness SDK, Luminate deployment)
- **governance** — governance, risk and compliance scope
- **pattern** — a reusable architecture pattern put forward for Enterprise Architecture
  approval (MCP Server Patterns)

A **pattern** spec carries one artifact the others do not: `specs/<spec_type>/<component>/pattern.md`,
the Sun Life design-pattern document, started from `docs/templates/pattern.md`. The D0–D3
gates are how the pattern was derived; `pattern.md` is what goes to the Enterprise
Architect, ETAB and the ISRA. `validate_specs.py` requires every section and header field
the template mandates — and reads that contract from the template itself, so there is no
second list to keep in step.

Optional free text `gate_status` carries the human note ("Discovery in progress —
stakeholder review phase"); it is not parsed.

### Layout: the folder is the spec_type

Specs live at **`specs/<spec_type>/<component>/`** — e.g. `specs/onboarding/aims-acp-integration/`.
`validate_specs.py` fails a spec whose folder does not match its `spec_type`, or anything
left at the old flat `specs/<component>/` location. Changing a spec's `spec_type` therefore
means `git mv`-ing the directory too, and then fixing its relative links (one level deeper
than the old layout: `../../../capability-map.md`, `../../<type>/<other-spec>/`).

Scripts never build a spec path by hand — they go through `scripts/spec_paths.py`
(`iter_spec_dirs`, `find_spec_dir`, `spec_rel`). `specs/epic-mapping.json` `spec_dir` is
`<spec_type>/<component>`; join on `component`, never on `spec_dir`. External readers
(`acp-reporting-agent`) resolve specs through that file, not by guessing a path.

After editing any `spec.yaml`, regenerate the derived files — `specs/README.md` and
`specs/epic-mapping.json` are both generated and must never be hand-edited:

```bash
python3 scripts/generate_spec_index.py && python3 scripts/validate_specs.py
```

## Common Commands

```bash
# ── Credentials ──
set -a && source .github/.env && set +a

# ── Sync specs to Confluence ──
python3 scripts/sync_to_confluence.py specs/platform/agent-registry/

# ── Regenerate the capability map diagrams (detailed + one-page summary) ──
python3 scripts/render_capability_map.py --export

# ── Sync the living capability map + summary sub-page + gap escalation process ──
# CONFLUENCE_SPACE_KEY is exported as DPEP by the shared credential file; override it
# inline or the pages publish into the wrong space.
CONFLUENCE_SPACE_KEY=T1KACP python3 scripts/sync_to_confluence.py --capability-map

# ── Regenerate spec index ──
python3 scripts/generate_spec_index.py

# ── Validate all specs ──
python3 scripts/validate_specs.py

# ── Git (spec gate advancement) ──
git checkout -b spec/agent-registry/d1
# ... edit d1-requirements.md ...
git add -A && git commit -m "spec(agent-registry): draft D1 requirements"
git push origin spec/agent-registry/d1
# Open PR → request team review → merge when approved
```
